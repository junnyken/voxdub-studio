### Confirmed gap

The existing real-dub gate invokes source code, conceptually equivalent to:

```text
python scripts/kiem_chay_that.py --den-cuoi
```

The package smoke test currently confirms only that the `.exe` starts and returns its basic expected values (for example `ok` and configured `api_url`). It does not execute a dub through the packaged `VoxDub.exe` nor verify a produced output video.

Therefore three release-critical claims remain unproven:

1. **I0-F:** The actual packaged executable can invoke its intended child workers and export a valid, non-silent dub video.
2. **I0-D:** A newly downloaded release works from a clean Windows installation, without accidentally consuming developer/source/sibling files.
3. **I0-E:** An upgrade installed beside a prior version reuses eligible engine/model/bin/configuration state truthfully and non-destructively.

### Architecture decisions that must remain unchanged

- The distributed Windows package remains PyInstaller `onedir` unless the audit proves an existing defect in that approach.
- Heavy engines remain in dedicated `.venv-*` child environments and are invoked through subprocesses. Do not import Whisper, torch, Demucs, VieNeu, NLLB, OCR, diarization, lipsync, PIL, or equivalent heavy libraries into the GUI/main executable process.
- Existing source-code real-dub verification remains; this MINI-SPEC **adds** packaged-executable coverage and does not replace source-route coverage.
- Existing release dry-run/no-publish condition remains intact during this work.
- Existing output validation rules (audio stream, non-silence/mean volume, duration checks) are reused rather than recreated with a second inconsistent definition.
- Existing upgrade behavior—discovering a prior installation only under the same parent directory—is preserved unless audit shows a documented bug.

## Goal

Prove, on Windows and without publishing a release, that the exact packaged release artifact can complete a controlled local end-to-end dub both from a clean install and as a same-parent sibling upgrade, while producing auditable evidence that subprocess workers, output audio, duration checks, and upgrade reuse behavior are correct.

## Constraints (Guardrails)

1. **Use the exact package artifact.** The gate must run the `VoxDub.exe` and files extracted from the ZIP/artifact generated by the same workflow. It must not run `python`, a repository checkout, an editable installation, or a copied-in source worker as a substitute.
2. **Dry run only.** This MINI-SPEC may build and upload CI artifacts but must not create/publish a GitHub Release, push a release tag, or change production deployment state.
3. **Additive coverage.** Do not remove, weaken, or redirect the existing `kiem_chay_that.py --den-cuoi` source-based gate.
4. **No hidden preinstalled engine assumption.** Clean-install verification must prove precisely which engines/resources are installed in the test environment. If the test needs a controlled installed engine fixture, it must be created through the packaged app’s supported setup route or an explicitly documented release-equivalent setup path.
5. **No GUI automation without audit.** First audit whether an existing CLI/headless/automation entry point reaches the same production application orchestration as the GUI. Use it only if it exercises the packaged executable and the same worker-launch path. If it does not, do not claim GUI-path coverage.
6. **No fake output success.** Do not accept an output file existing as sufficient. It must be readable and have audio stream + non-silence evidence + valid duration evidence.
7. **No silent fallback to source or old install.** Every executable path, worker path, `sys._MEIPASS`/app root, virtual-environment path, model path, and output path used during the test must be logged. A path outside the candidate package/test sandbox is a failure unless it is an explicitly allowed same-parent prior-install resource in the upgrade gate.
8. **No release green if gate is blocked.** A missing automation entry point, unautomatable GUI, network dependency, unavailable runner capability, or missing engine must result in `blocked` with evidence—not a skipped green test.
9. **Preserve reuse semantics.** The upgrade gate may verify reuse; it may not change/rewrite/remove prior version engines, models, binaries, or configuration as part of detection.
10. **Do not leak secrets.** Upgrade fixtures use non-production token/config values. Logs and artifacts must redact token/API-key values.
11. **Keep test fixture legal and deterministic.** Use project-owned or explicitly permitted small fixture media. Do not embed/download third-party copyrighted video as the required CI fixture.
12. **Scope discipline.** Do not add visual prompts, providers, H4d activation, image generation, new TTS engines, or release publication logic.

## Scope

### A. Audit and route selection

Before implementation, inspect and report:

1. How the package smoke test launches `VoxDub.exe` and reads `ok`/`api_url`.
2. Whether `VoxDub.exe` already exposes a supported command-line/headless/test command that reaches the same application orchestration and worker launcher used by the GUI.
3. Whether an existing local IPC/control server/API is started by the packaged app and can be used as an authenticated test control plane.
4. Whether the existing CLI `voxdub dub` is bundled with the `.exe`, invokes the packaged app paths, and uses the same subprocess worker abstraction; do not assume this.
5. How `scripts/kiem_chay_that.py --den-cuoi` provides deterministic manual translation, selects VieNeu, waits for completion, and probes the output.
6. Existing output validators, including FFprobe/ffmpeg commands and mean-volume/duration thresholds.
7. Existing upgrade discovery code: parent/sibling directory rules, `.venv-*`, `models/`, `bin/`, `.env`, configuration migration, and log paths.
8. Exact artifact layout after PyInstaller and ZIP extraction.

### Required route decision

Choose exactly one implementation route after audit:

#### Route A — Packaged executable control interface

Use this only if `VoxDub.exe` provides an existing supported CLI, local API, control server, or test mode that reaches the same production orchestration and subprocess worker launcher as the GUI.

The test must launch the package executable first, submit/run the controlled dub using that interface, wait for terminal result, and validate the output.

#### Route B — Minimal packaged test command

Use this only if no suitable existing interface exists. Add a **narrow, explicit, test-only or documented diagnostic command** to the packaged executable that invokes the already-existing production orchestration/service layer; it must not reimplement dubbing logic in a parallel test pipeline.

The command must:

- Require explicit paths for input fixture, deterministic translation fixture, output directory, and evidence directory.
- Be disabled or unreachable from normal GUI interaction unless explicitly invoked with the test/diagnostic argument.
- Return a non-zero exit code on any failed stage.
- Emit a structured result JSON with safe paths, selected route, stage results, worker evidence, and output probe results.
- Not require cloud provider access or charged Vox activity.

**Route B is not permission to create a second dub engine.** It is an adapter around the existing app orchestration that lets CI exercise the package.

### B. Controlled fixture and deterministic input

Create/reuse only the smallest suitable fixture set:

| Fixture | Requirement |
|---|---|
| Source video | Short, stable, project-owned/permitted, local file; enough speech/audio to verify ASR and output audio |
| Expected/controlled transcript or manual translation | Deterministic local fixture; avoids paid/cloud translation and avoids network variance |
| VieNeu voice/config | Existing local default/test-safe voice path; no cloud TTS |
| Output directory | Created fresh inside the candidate sandbox |
| Evidence directory | Created fresh inside CI workspace/artifact collection path |

The fixture must be short enough for Windows CI but long enough to detect silent output and meaningful duration mismatch. Audit must document its duration, hash, language, and licensing/ownership basis.

### C. I0-F — packaged end-to-end dub gate

#### Required execution flow

1. Build candidate `onedir` application and ZIP artifact as currently done.
2. Create a fresh extraction directory from the ZIP/artifact. Do not execute from `dist/` if the user downloads a ZIP; test the closest user-delivery form.
3. Launch the packaged `VoxDub.exe` through the selected Route A or Route B.
4. Run the minimum deterministic local dub path:
   - local fixture input;
   - audio extraction;
   - ASR through the applicable installed worker;
   - controlled/manual translation fixture;
   - VieNeu TTS through its child worker;
   - merge/export through the existing production path.
5. Wait for a terminal success/failure state with timeout appropriate to the existing source real-dub gate.
6. Collect structured result, app logs, child-worker logs, and output media.
7. Probe the output with the project’s existing validators.

#### Required assertions

- Candidate executable path is inside the extracted candidate package.
- Input, work, output, and evidence paths are inside the test sandbox.
- No repository checkout/source application path is used for the main app or workers.
- Every heavy worker invoked is launched through the existing subprocess boundary.
- Output exists and is readable by the existing probe.
- Output has at least one audio stream.
- Output passes existing non-silence/mean-volume criteria.
- Audio and video durations are valid and meet the existing timing contract for this route.
- Any missing engine/resource produces a distinct actionable failure, not “no content” or a generic error.
- Logs/artifacts identify the candidate package version/SHA and fixture hash.

#### Required evidence artifact layout

```text
packaged-dub-evidence/
  result.json
  environment.json
  candidate-artifact.json
  executable-path.txt
  input-fixture.json
  app.stdout.log
  app.stderr.log
  worker-launches.jsonl
  worker-*.log
  output-probe.json
  output-video.mp4             # when CI artifact-size policy allows
  output-video.sha256
  failure-screenshot-or-log/   # only when applicable
```

`result.json` must make failure stage explicit: `startup`, `input`, `asr`, `translation_fixture`, `tts`, `merge`, `probe`, `timeout`, or `unexpected`.

### D. I0-D — clean-install gate

#### Sandbox requirements

Create a fresh root directory that has:

- no prior VoxDub installation under the same parent;
- no source checkout or artifact staging directory reachable through the app’s normal sibling-discovery logic;
- no inherited `.venv-*`, `models/`, `bin/`, `.env`, or user app-data state unless the audit documents an unavoidable runner-global path and it is explicitly cleared/isolated.

The test must log all relevant environment variables and candidate discovery paths while redacting secrets.

#### Required execution

1. Extract the candidate ZIP into the clean-install root.
2. Run existing package smoke test.
3. Confirm package manifest/resources required for the selected controlled pipeline exist physically.
4. Prepare the required engine state using one of these audited approaches:
   - **Preferred:** invoke the same packaged setup/installer path exposed to users.
   - **Allowed only if setup is not CI-automatable:** create a pre-seeded test cache using the exact same setup script/format/version that the release would create, and record this as a remaining coverage limit. This does not count as testing the installer UX.
5. Execute I0-F packaged real dub from this clean installation.
6. Confirm the result has no worker/resource path outside the clean sandbox except operating-system dependencies such as system ffmpeg only where the package design explicitly permits it.

#### Negative assertions

- A component absent from the clean package/install cache must be reported as unavailable with the existing actionable instruction.
- The app must not claim it reused a prior engine/model/configuration.
- No output or log may show a source checkout path used as fallback.

### E. I0-E — same-parent sibling-upgrade gate

#### Fixture layout

Create a controlled parent directory containing two siblings:

```text
<upgrade-parent>/
  VoxDub-previous/
    .venv-vieneu/              # marker or release-equivalent fixture
    models/                    # marker or release-equivalent fixture
    bin/                       # marker fixture
    .env                       # non-production fixture; secrets redacted in logs
    upgrade-fixture-manifest.json
  VoxDub-candidate/
    ... extracted candidate ZIP ...
```

The previous sibling may be a prior real artifact or a narrowly documented representative layout. Prefer a prior real artifact when stable and available. If a marker layout is used, it must match the exact discovery contract rather than inventing a synthetic path structure.

#### Required execution

1. Hash/record all fixture files in `VoxDub-previous/` before launching the candidate.
2. Launch candidate `VoxDub.exe`.
3. Capture discovery/migration logs and structured state where available.
4. Verify each reusable item independently:
   - `.venv-vieneu` or required TTS environment;
   - `models/`;
   - `bin/`;
   - configuration/token migration behavior.
5. Verify the candidate never modifies or deletes the prior sibling’s source files unintentionally by comparing post-run hashes/manifest.
6. Run I0-F packaged real dub using the discovered/reused candidate configuration where possible.
7. Validate output as in I0-F.

#### Required negative subcases

1. **Different parent:** Candidate placed under a different parent must not claim automatic reuse.
2. **Missing component:** Prior sibling lacks one component; candidate must not claim that component was reused.
3. **Invalid config:** Prior `.env` is malformed or has an invalid non-production token; candidate must not reveal its value and must show/record an actionable migration/configuration state.
4. **No destructive migration:** Candidate may copy/migrate eligible configuration according to existing design but must not delete/overwrite the prior sibling’s files.

## Design Choice

The selected design is a **package-first evidence gate**:

\[
\text{build candidate ZIP}
\rightarrow
\text{extract candidate to isolated sandbox}
\rightarrow
\text{launch VoxDub.exe}
\rightarrow
\text{invoke existing production orchestration}
\rightarrow
\text{run child workers}
\rightarrow
\text{export output}
\rightarrow
\text{probe output}
\rightarrow
\text{retain auditable evidence}
\]

The same package-first route runs twice:

1. **Clean install (I0-D):** no discoverable prior sibling state.
2. **Same-parent upgrade (I0-E):** controlled prior sibling state, with preservation and negative cases.

### Why this design

The existing source route has already demonstrated that the source pipeline works. It cannot prove that PyInstaller resource resolution, worker inclusion, subprocess paths, post-extraction layout, sibling discovery, or user-facing upgrade behavior work in the artifact a Windows user downloads.

Running the package rather than reusing Python code is the only meaningful way to close that boundary. Reusing existing app orchestration and existing output validators avoids a parallel “test-only dub pipeline” that could pass while the product fails.

### Explicitly rejected designs

- **“Smoke test passed, so package is good.”** Rejected: startup does not prove ASR/TTS/export.
- **Run `python scripts/kiem_chay_that.py` after packaging.** Rejected: still tests source code.
- **Copy source workers next to the package during CI.** Rejected: hides missing package files.
- **Test only upgrade.** Rejected: clean users and upgrade users have different failure modes.
- **Test only clean install.** Rejected: reuse/migration behavior is a product promise with separate risk.
- **Automate GUI clicks without audit.** Rejected unless no valid package control boundary exists; brittle GUI automation is not automatically proof of production orchestration.

## Test Plan

### Unit tests

1. Candidate-path validator rejects executable/worker/resource paths outside permitted sandbox roots.
2. Evidence serializer redacts token/API-key values.
3. Package control command/config parser rejects missing required input, translation fixture, output, or evidence paths.
4. Package control command returns non-zero result for each terminal-stage failure.
5. Upgrade discovery identifies only same-parent sibling candidates.
6. Upgrade discovery rejects different-parent sibling state.
7. Upgrade reuse summary does not claim reuse for absent components.
8. Prior-sibling preservation checker detects modified/deleted files.
9. Output result validator requires audio stream, non-silence data, and duration probe result.
10. Removing required package worker/resource causes manifest/path validation to fail.

### Integration tests

1. Build candidate `onedir` app and user-delivery ZIP.
2. Extract ZIP into isolated clean sandbox and launch `VoxDub.exe`.
3. Run I0-F package route with fixture through the chosen Route A/B.
4. Verify logs show candidate-local subprocess worker paths and no source fallback.
5. Probe output using existing project tooling.
6. Run I0-D clean-install package route, including engine setup behavior and negative missing-resource state.
7. Run I0-E same-parent sibling upgrade route and compare prior-sibling pre/post manifests.
8. Run I0-E different-parent negative case.
9. Run I0-E missing-component negative case.
10. Run I0-E malformed-config redaction/actionability negative case.
11. Verify dry-run workflow skips release publication while still uploading evidence.

### Regression tests

1. Changing the package route to invoke `python`/repository path instead of `VoxDub.exe` must fail a route assertion.
2. Removing one packaged worker needed by the fixture must fail before/at worker launch with the exact missing resource named.
3. Removing audio stream/non-silence/duration checks must fail the output-validator test.
4. A source path appearing in a clean-install worker log must fail the clean gate.
5. A candidate in another parent directory falsely reusing an old model/venv must fail the upgrade gate.
6. A candidate modifying a prior sibling file must fail the upgrade preservation gate.
7. A malformed token printed in evidence must fail redaction test.
8. Changing workflow condition so packaged gates do not run before publish eligibility must fail workflow/static validation where project tooling supports it.

### Live verification

Execute on `windows-latest` or a documented equivalent Windows environment using the exact dry-run candidate ZIP.

#### Run 1 — I0-D clean install + I0-F package dub

- Fresh isolated parent.
- Candidate ZIP extracted.
- Packaged executable launched.
- Engine setup path recorded.
- Fixture dub completed.
- Output probes recorded.
- Evidence artifact uploaded.

#### Run 2 — I0-E upgrade + I0-F package dub

- Controlled previous sibling plus candidate sibling under same parent.
- Previous state manifest recorded pre-run.
- Candidate launched and reuse/migration decisions recorded.
- Previous state manifest compared post-run.
- Fixture dub completed using candidate/reused route where possible.
- Output probes recorded.
- Evidence artifact uploaded.

#### Run 3 — I0-E negative cases

- Different parent: no false reuse.
- Missing prior component: no false reuse.
- Invalid non-production config: no secret leakage and actionable state.

A run may be labeled `blocked` only with captured evidence and a precise blocker. It is not a successful verification.

## Success Criteria

This MINI-SPEC is complete only when all statements are true:

1. The dry-run workflow runs the exact downloaded-form candidate package—not source Python—to execute a controlled end-to-end local dub.
2. The packaged run demonstrably launches required heavy workers through the existing subprocess architecture.
3. The candidate output video is readable, has an audio stream, passes the established non-silence check, and meets the existing duration contract for the exercised route.
4. Clean-install verification proves no source checkout, old sibling, or hidden runner cache was used as an unintended fallback.
5. Same-parent sibling upgrade verification proves eligible reuse works and prior installation contents are not destructively modified.
6. Different-parent, missing-component, and invalid-config upgrade cases do not yield false “reused” success and do not leak secret values.
7. The existing source-code real-dub gate remains enabled and green; package-level coverage is additive.
8. Evidence artifacts make executable path, package checksum, candidate SHA, worker paths, fixture hash, output probes, and terminal result inspectable after CI completes.
9. The workflow stays dry-run/no-publish while this MINI-SPEC is introduced and verified.
10. `FEATURES.md` and `TEST_LOG.md` accurately state the result; if any gate is blocked or fails, they do not claim packaged release verification.
